# 原安装恢复的公共终结协议

版本保持 `1.0.0.0`，继续先完成内部验收候选。本检查点接续[原生恢复权限](2026-10-05-maintenance-recovery-authority.md)，把恢复结果接到公共事务、认证 helper 会话、父进程协调器和界面结果展示。原生恢复执行器、首次准备捕获、私有恢复决定及按钮入口仍需装配，当前不能据此宣称产品恢复已经可用。

## 行为

新增 `OriginalRestored`，表示原安装的后置条件已被独立验证。它只允许同账户、未启用重新关联的 Repair 从 `Prepared` 或 `MachineReserved` 进入，代数分别为 2 或 3。包提交后不能进入此分支；已恢复分支不能再进入候选部署或候选 `Verified`。保存继续使用前一记录摘要和唯一合法后继做比较，不允许跳代。

新增 `restore-original` 和 `clear-original`，保持既有严格、有限大小、无任意路径的命令格式。helper 必须具备明确的原安装恢复能力，专用清理还要求明确的原恢复存储权限；普通安装执行器和普通 `ClearVerified` 不能代替。缺少能力时保留事务并拒绝执行。

原恢复完成后，helper 保存准确的公共终态，再独立观察。恢复提交回执丢失时，只重验已经提交的原恢复结果，不再次修改服务。清理回执丢失、公共记录已经不存在时，仍须重新核对私有完成证据及原安装后置条件。清理确认前不会报告成功。恢复清理不写卸载终结记录、不删除目录归属记录，也不调用卸载目录清理。

父进程使用原有执行互斥和已验证候选寿命，接收 helper 的准确终态及清理收据，并通过只读事务视图重新核对。提交恢复后取消会留下可继续的恢复终态；普通“继续”在此终态只完成原安装的重验与清理，不再次部署候选。界面显示“已保留原安装”，并拒绝将安装、卸载、未清理事务或不匹配的结果解释为原恢复成功。

同时修正旧验证中的零代数漏洞：未支持的操作/阶段组合此前可能因默认期望代数为 0 而通过 `Validate`。现在所有代数为 0 的记录都被拒绝，包含每个已定义操作和阶段的组合回归。

接下来实现私有恢复决定与可重启阶段，再装配首次准备捕获、原生恢复执行器及 UI 入口。首次捕获必须区分完整可恢复的原安装和原安装已损坏的正常修复；重放不能把已准备的服务重新当作原服务。正常继续完成候选和保留原安装都需要完成私有记录的终结，避免首次记录残留阻止下一次维护。全部完成后执行原生故障和跨进程验收；本检查点不关闭完整生产目标。

# Windows TCP 监听归属检测兼容性

10 月 6 日恢复开发后，确认主线 `01de538` 工作区干净、两项 CI 成功，测试服务器仍运行此前 `e218d85` 的 `1.0.0.0` 内部候选，应用已退出且无公共安装事务。本次处理此前开发机 Windows 11 Insider 26220 的 TCP 监听归属检测失败，版本保持 `1.0.0.0`。

## 原生观察

原实现从 `TCP_TABLE_OWNER_PID_ALL` 读取 IPv4 行，以 `State == 2` 判断监听。使用原源码和仅属于探针进程的回环端口复现：开发机返回状态 `0`，导致监听检查失败；已建立连接的完整端点与 PID 检查正常。没有修改开发机代理、路由、防火墙或服务。

进一步直接读取原生缓冲区，比较监听表、连接表、全部表及 `GetTcpTable2`，排除了托管结构字段解析差异。两台机器使用相同 `.NET 10.0.12`，观察到：

| 套接字阶段 | Insider 26220 监听专表 | Server 26100 监听专表 |
| --- | --- | --- |
| 仅绑定，尚未监听 | 无对应行 | 无对应行 |
| 正在监听、等待接受或已有连接 | 一行，原始状态 0 | 一行，原始状态 2 |
| 关闭监听，已接受连接仍存活 | 无对应行 | 无对应行 |

`GetTcpTable2` 在开发机也返回监听状态 0；切换到该 API 不能解决本次差异。Microsoft 为 `TCP_TABLE_OWNER_PID_LISTENER` 明确定义了只返回监听端点的契约，见[表类型说明](https://learn.microsoft.com/en-us/windows/win32/api/iprtrmib/ne-iprtrmib-tcp_table_class)；行的字段定义见[MIB_TCPROW_OWNER_PID](https://learn.microsoft.com/en-us/windows/win32/api/tcpmib/ns-tcpmib-mib_tcprow_owner_pid)。

## 修正

监听检查改为请求 Windows 的监听专表，以表成员身份判定是否监听，继续匹配准确 IPv4 回环地址、端口和唯一预期 PID。没有把全部表中的状态 0 当作监听，也没有把已建立连接用于推断监听仍存在。

已建立连接检查继续读取全部表，并要求状态为 `ESTABLISHED`、服务器和客户端端点完整匹配且所有者唯一。原有缓冲区大小、行数、重试次数和原生读取失败拒绝策略保持。

新增原生回归覆盖仅绑定端口，以及关闭监听但保留已接受连接的情况。后者同时要求监听验证失败、现存连接的正确 PID 验证成功、错误 PID 验证失败，防止用全部表忽略状态的简单改法产生误判。修正前 8 项中 2 项失败，修正后 8 项全部通过。相同修正源码的只读原生探针在 Insider 与 Server 均通过，源码 SHA-256 为 `29b04694fcca347ca10b9da83e760e72fc0c84bcb21fb7586ebbba5919651529`。

本机完整主程序集 3,964 项通过、0 失败、0 跳过，没有排除原生监听测试。18 项目 Release/x64 构建零警告、零错误，完整 `dotnet format --verify-no-changes --no-restore` 检查通过。修正前的失败 TRX 与修正后的完整结果分别保留，避免把单项重复计入全量通过数。

原始表对照、失败与通过 TRX、两台机器的探针收据和格式日志位于被 Git 忽略的 `artifacts/verification/tcp-compatibility-20261006/`。该记录区分源码探针验证与安装包验收：服务器上已安装的旧候选尚未包含本次修正，后续需构建并验证准确新候选。

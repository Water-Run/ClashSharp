# 已中止候选目录的安全回收

[TUN 文件占用验收](2026-10-06-tun-data-recovery-acceptance.md)发现：导入在数据代指针提交处失败，原接管已补偿且候选资源已关闭，未发布目录仍留在磁盘上。直接删除也会破坏后续读取，因为已完成的恢复日志仍引用该候选，并要求它的物理目录存在。

新增两项回归复现了目录残留与已完成日志读取失败；未完成日志遇到缺失候选的拒绝对照通过。首次测试编译遗漏命名空间，修正后得到两失败、一通过的有效红测。实现修正后的首次复验还发现夹具读取了已退休容器，改为核对原容器；这些夹具错误与产品红测分别保留。

## 实现边界

恢复日志确认完成时清空仅用于恢复的候选引用，仍保留完成标记、操作身份、基线及其外部状态。版本一的记录结构和既有读取兼容；版本、摘要、路径、身份及未完成记录的物理目录校验继续执行。

协调器在原网络状态补偿、候选作用域完全释放和恢复日志完成之后，尝试删除该次操作确认中止的未发布候选。回收器核对独占许可、完整中止状态、未提交/未发布状态、候选资源已释放、准确目录身份、实际指针仍为原基线，以及没有待恢复记录。

删除期间持有普通目录链的 Windows 读取句柄，同时持有当前指针与恢复日志的读取句柄，阻止改名和替换。先检查完整候选树的归属、链接和数量/深度上限，再逐项非递归删除；身份标记最后移除。文件被其他进程占用时保留标记，释放后可以按同一身份重试。句柄行为依据 [CreateFile 的目录与共享规则](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew)，并通过实际 Windows 文件操作验证。

回收失败会与原操作异常一起记录，已经核实恢复的原应用继续开放普通操作。资源释放失败、未完成恢复和不确定提交仍按原有恢复流程保留。成功提交的旧数据代、初始创建失败或尚未获得完整资源释放证明的目录继续保留；本次不增加全盘扫描或按目录年龄删除。

## 验证与后续

新增九项回归覆盖：提交失败后的实际目录回收、已完成与未完成日志的读取差别、未完成恢复拒绝、准确重复执行、目录链/指针/日志替换阻断、链接子目录拒绝、文件占用后重试、实际指针变化拒绝，以及回收失败时原接管与普通操作保持。最终主程序集 3,973 项全部通过，零失败、零跳过；18 项目 Release/x64 构建零警告、零错误，最终格式检查通过。

首次完整回归为 3,972 项通过、一项架构检查失败：检查器要求显式等待、返回或持有 `Task.Run`，没有接受表达式形式的返回。改用显式 `return Task.Run(...)` 后重新构建和运行全部测试通过，架构检查保持原规则。

证据位于 `artifacts/verification/candidate-cleanup-20261006/`。本机检查只操作独立临时目录，没有修改开发机代理、服务或证书。后续准确 `8892c5d` 内部候选已在服务器完成原生指针占用、自动回收、重启和导入重试，详见[实机复验](2026-10-06-candidate-cleanup-native-acceptance.md)，版本保持 `1.0.0.0`。

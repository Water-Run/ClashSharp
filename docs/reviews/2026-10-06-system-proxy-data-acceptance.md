## TUN 转发、内核中断与退出

使用恢复的数据代、默认 TUN 偏好和规则模式启动服务接管。内核 PID 16488 位于会话 0，父进程为服务 29252；Meta 网卡 Up，有九条接口路由。系统代理保持关闭及原始指纹，此模式没有普通 mixed-port 监听。

独立 HTTP 探针明确关闭代理，解析连通性目标后校验系统选中的路由属于 Meta 接口，再向该地址发送带正确 Host 的请求。响应为 200 且内容匹配，接口收发计数均增长。这证明实际 TUN 路由下的请求通过，未把系统代理转发替代为 TUN 证据。

05:52:15 UTC，在核对准确 PID、创建时间、可执行文件摘要、父服务和会话后，定点结束上述内核。服务自行创建新内核 PID 20468；应用与看门狗未重启，服务 PID、数据代和设置修订号保持。05:52:20 的观察确认 Meta 重新可用，随后相同的无代理 HTTP 探针再次通过。这只覆盖一次内核异常退出，不代替服务崩溃、应用崩溃或多次重试耗尽场景。

## 过程差错和范围限制

滚动时误用键盘导航，曾将语言选项切到韩语，随即通过实际下拉框恢复自动检测；它不计为语言验收。一次 SSH 名称解析失败未投递保存点击，重新观察文件对话框后使用 IPv4 连接保存。名为 `after-active-import` 的收据实际位于第二次确认之前，仍为旧数据代；真正的提交后证据是 `active-import-terminal`。

TUN 的首个观察误用了要求系统代理开启的探针，因此被前置条件拒绝；随后改用无代理 TUN 路由探针。首次中断尝试的时间对象比较也被身份检查拒绝，未结束进程；核对原始时间、摘要和父服务后，以规范 UTC 字符串重新匹配再实施一次中断。`tun-after-core-interruption` 是这次未变更状态的保留观察，真正恢复后的收据为 `tun-core-restarted`。这些探针或操作差错均不计为产品失败或成功场景。

G05 仍需活动 TUN 下的导入、全部重置和清除，以及两种网络模式的文件占用、持久化失败、提交后应用失败、重启中断和旧页面输入。G06 仍需应用/服务实际异常、看门狗与登录恢复、退出失败重试、第三方代理归属及重试耗尽。Windows 11 完整安装器初始化、全新安装强制 GC、其余页面与安装矩阵、发行材料集成和正式签名也继续保留。

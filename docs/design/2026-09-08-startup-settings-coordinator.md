# 开机启动设置的统一事务

设置页此前先保存开关，再调用应用动作更新 Windows StartupTask。应用动作
读取的补偿基线因此可能已经是新值；页面随后用自己的旧值回写，还可能覆盖
后端已经完成的恢复结果。四项回归在旧实现上复现了提前保存和覆盖结果的问题。

现在 `StartupSettingsCoordinator` 在 Application 层统一负责普通启动设置变更。
设置页和共享应用动作使用普通入口，触发器传入自己已有的 admission lease；
两者由同一个 AppHost 单例串行执行。适配器只连接原有 AppSettingsService 和
StartupLaunchService，不创建额外设置存储，也不在构造函数中访问 Windows。

## 应用和恢复

- 取得准入许可后等待协调器，再读取原有偏好及实际注册状态。两项基线独立保存，
  不能假设 Windows 当前状态一定等于上次保存的偏好。
- 实际状态未知、平台不可用或取消发生在修改前时，直接结束，不尝试平台修改
  或设置写入。排队中的普通操作响应关闭准入发出的撤销信号。
- 开始修改后保持许可，完整等待注册、重新读取验证和偏好提交；页面取消不再
  中断这段操作。偏好只在 Windows 确认目标状态后写入，并重新读取确认。
- 非致命失败分别恢复实际注册基线与偏好基线，继续验证两者。Windows 补偿失败
  仍尝试恢复偏好；任何未完成补偿都通过 `StartupSettingsRecoveryException`
  保留原始错误和恢复诊断。致命错误图继续传播。
- 已持有许可的触发器调用不会重复准入或释放调用方的许可。重置和导入仍使用
  原有独占保留事务，其 StartupTask 参与者只更新外部注册，不重复保存偏好。

页面只暂存选择并等待应用动作；失败后重新读取后端偏好，不用页面旧值反向
写入。连续选择按最新请求继续应用，命令完成间隙的请求保留在受跟踪的任务中，
重置开始前会等待该任务排空。旧同步回调的设置写入仅保留在 UNIT_TESTS 夹具中，
生产构造必须提供完整异步应用动作。

## 验证

新增 47 项回归：应用协调器 34 项、真实适配器配合模拟 Windows 平台 7 项、
页面行为及排空 5 项、共享装配架构约束 1 项。覆盖不同原有偏好/实际状态、部分
平台修改、提交前后失败、无法验证、两种补偿失败、取消、准入撤销、串行请求、
调用方许可保持和致命错误图。此前两项请求顺序测试改为检查第二次后端提交失败
仍保留第一次已提交结果，页面不再提供提前持久化入口。

主程序全部 2577 项通过、0 失败、0 跳过；18 项目 Release x64 构建 0 警告、
0 错误；完整 format 检查 1431 个文件、0 处变更。实际结果、四项初始失败和
16 个源文件摘要见 `artifacts/verification/local-validation-m3l.json`。更新旧的
源码位置检查期间，两轮检查失败单独保留，不计入最终通过结果。

上一笔文档提交 `e552479` 的 CI 34197887559 中，退出交接测试在删除 Triggers.db
时遇到占用，主程序为 2529 通过、1 失败，后续 Installer 测试未运行；打包任务
单独成功。失败报告保留为 `ci-validation-m3k-docs-failed.json`。代码检查发现该
夹具用两秒 WaitAsync 放弃等待，却没有取消并排空数据库使用者；现在为运行器
和交接确认传入共同的 30 秒取消期限，等待两者结束后才清理。本地该用例已通过，
不据此推定原 CI 的所有中间状态或宣称发现了生产数据库句柄泄漏。

本轮 Windows 注册为模拟，适配器测试明确确认设置使用内存回退；没有修改开发机
开机启动、代理、证书或安装状态。生产设置仍是唯一 LocalSettings authority，
完整设置代际迁移与实际 Windows 页面交互继续验收。
